# Framework Mapping 规范

## 1. 为什么每章都必须做 Mapping

第二阶段最容易出现的假学习是：

> Codex 把项目写出来了，页面也能聊，但你只学会了复制框架示例。

因此每个框架项目 README 必须包含 Mapping。

## 2. 标准表格

```markdown
## Framework Mapping

| 能力 | 手写 Baseline | 当前框架 | 框架替代程度 | 仍由我们负责 |
|---|---|---|---|---|
| 模型调用 | LlmClient | ... | 高/中/低 | ... |
| Tool 定义 | Tool interface | ... | ... | ... |
| Tool Loop | AgentRunner while | ... | ... | ... |
| Conversation | ... | ... | ... | ... |
| Memory | ... | ... | ... | ... |
| State | ... | ... | ... | ... |
| Trace | ... | ... | ... | ... |
```

## 3. 必答问题

### A. 框架真正删除了哪些代码？

必须指出具体类/方法，而不是写“简化开发”。

### B. 哪些复杂度只是被搬走？

例如 Tool Loop 被框架接管，并不意味着：

- Tool 描述不需要设计；
- 权限不需要控制；
- 失败语义不需要定义。

### C. 控制权去哪了？

例如：

- 能否控制每一步 loop？
- 能否修改 tool result？
- 能否插入人工审批？
- 能否查看 intermediate messages？

### D. 框架边界在哪里？

哪些依然属于：

- Domain；
- Repository；
- Application Service；
- UI；
- Security。

## 4. 代码量不是唯一指标

不要只比较 LOC。

还要比较：

- 心智负担；
- 可观测性；
- 控制粒度；
- 测试难度；
- 框架锁定；
- 生态；
- 长任务能力；
- Multi-Agent 能力。

## 5. 代码内嵌对比：`@FW-CMP` 注释规范（强制）

> 从 Ch02 起，每个框架模块的 Java 代码 **必须** 在"框架接管了手写版什么"的关键点打上 `@FW-CMP` 标记。
> 优秀案例：**`spring-ai/basic`**（本规范的所有示例都来自该模块，可直接参考）。

### 5.1 目的

让读者（未来的自己）**不用回到手写版仓库翻代码**，就能在框架代码旁直接看到：

1. 这一步手写版是怎么写的（3-8 行精简片段）；
2. 框架现在是怎么写的（就是注释下方那行代码）；
3. 差异本质是什么、牺牲了什么控制权。

### 5.2 标记格式

**类级 Javadoc**（每个框架入口类必须有）：

```java
/**
 * 类功能一句话说明。
 *
 * <p>@FW-CMP 本类对应手写版 {@code agent-harness/XXX}（职责一句话）。
 * 手写版要手动做什么什么；本类只剩什么。
 *
 * <p>完整对比见 {@code docs/comparisons/chNN_<章节名>.md}。
 */
```

**行内对比注释**（只在"框架替我做了事"的关键行/块上方）：

```java
// @FW-CMP [<类别>] <差异主题一句话>
//   手写（<手写版文件/方法>）：
//     <3-8 行手写代码骨架，贴原始代码片段>
//   框架（下方）：
//     <一行说明框架怎么写>
//   差异：<一句话本质差异>；
//   代价/取舍：<失去了什么 / 得到了什么>。
//   完整版见 docs/comparisons/chNN_<章节名>.md#<锚点>
<实际代码>
```

### 5.3 类别枚举

统一使用以下类别（方括号内），便于按类过滤：

| 类别 | 含义 |
|---|---|
| `PROMPT` | 流程/意图从代码搬到提示词 |
| `TOOL_LOOP` | 多轮工具调用循环的归属 |
| `SCHEMA` | 工具 schema / 参数定义的生成方式 |
| `TOOL_DISPATCH` | 工具查表 / 分派 / 结果回填 |
| `ERROR_SEMANTIC` | 工具错误如何回馈给模型 |
| `HTTP` | HTTP 客户端、请求/响应序列化 |
| `CONTEXT` | 对话上下文的构建与维护 |
| `MEMORY` | 记忆 / 长期状态 |
| `STATE` | 运行时状态、Checkpoint |
| `TRACE` | 可观测性、Trace 事件 |
| `HITL` | 人工审批 / 中断恢复 |
| `MULTI_AGENT` | 多智能体分派 |
| `CONFIG` | 装配、依赖注入、配置加载 |

新章节如出现上表没有的类别，先在对应 `chNN_*.md` 对比文档中定义，再用到代码里；并在本表补一行。

### 5.4 加标记的位置（只在以下三类加）

1. **类级 Javadoc**：框架入口类（Agent / Main / Tools 类），说明"本类对应手写版谁"。
2. **"框架替我做了事"的那一行 / 那一块**：如 `.tools(...)`、`.call()`、`ChatModel.builder()`。
3. **"如果不用框架我得自己写一段逻辑"的代码块入口**：如 Main 里的装配块、自定义 Advisor。

### 5.5 不加标记的位置（避免刷屏）

- 纯业务代码：`XxxService`、`XxxRepository`、领域模型（`Task`、`TaskStatus` 等）；
- POJO / record（无逻辑可对比）；
- 测试代码（除非测试本身就是对比点，此时在测试类 Javadoc 加一条说明即可）；
- 框架不管的配置加载（如 `ModelConfig` 读 `.env`）。

**判断准则**：如果删掉这个类/方法，手写版也要写一份几乎一样的——就不加。

### 5.6 可搜索性

全局搜索所有对比点：

```bash
grep -rn "@FW-CMP" <模块路径>/src
```

按类别过滤：

```bash
grep -rn "@FW-CMP \[TOOL_LOOP\]" <模块路径>/src
```

## 6. 章节对比文档：`docs/comparisons/chNN_*.md`（强制）

> 每完成一个框架章节，**必须**在 `docs/comparisons/` 下产出一份对比文档。
> 命名：`chNN_<章节关键词>.md`，例如 `ch02_spring_ai_basic.md`、`ch03_spring_ai_stateful.md`。
> 优秀案例：**`docs/comparisons/ch02_spring_ai_basic.md`**。

### 6.1 文档结构（按此模板写）

```markdown
# ChNN <章节标题> — 手写 vs 框架 完整对比

> 本文件是第 N 章的完整对比文档，对应代码模块 `<模块路径>`。
> 代码里所有差异点都打了 `@FW-CMP` 标记；每个标记末尾有 `#N-xxx` 锚点指向本文档对应章节。

## 本章节差异点导航

| # | 类别 | 位置（框架版） | 一句话差异 |
|---|---|---|---|
| 1 | PROMPT | ... | ... |

## 1. <类别> — <差异主题> {#锚点}

**类别**：`XXX`
**框架版位置**：<文件链接 + 方法/行>

### 手写版（agent-harness）
```java
// 完整手写方法 / 关键类，不省略
```

### 框架版（本模块）
```java
// 完整框架调用，不省略
```

### 差异本质
| 维度 | 手写 | 框架 |
|---|---|---|
| ... | ... | ... |

### 取舍
- 得：...
- 失：...
- 框架不管：...

### 实际运行证据（可选）
<真实演示输出、日志、测试断言>

---

## 本模块没有打标记的类
<列出哪些类是"框架不管的业务代码"，并说明为什么>

## 本章 `@FW-CMP` 标记清单
<grep 命令 + 输出>
```

### 6.2 写作原则

1. **代码为主，文字为辅**：手写版代码**贴完整方法**，不是精简版；精简版只出现在 Java 注释里。
2. **按运行时顺序组织章节**：启动 → 装配 → 调用 → 循环 → 返回。不按"类"组织。
3. **双向链接**：Java 注释末尾 `完整版见 docs/comparisons/chNN_xxx.md#anchor`，文档表格里"框架版位置"反向指向 Java 文件。
4. **锚点编号与文档目录一致**：`#1-prompt`、`#2-tool-loop`、`#3-http`、`#4-schema`、`#5-error-semantic`……编号即目录顺序。
5. **明确"本章刻意没做什么"**：手写版有但本章框架版没实现的能力（如 Checkpoint / HITL / Multi-Agent），在"差异本质"表格里单独成行写"**本章未实现**"，不要让读者误以为框架不支持。

### 6.3 与模块 README 的 `Framework Mapping` 表的关系

- **README 的 Framework Mapping 表**：宏观、按"能力维度"（模型调用 / Tool 定义 / Tool Loop / Memory / ...）、回答五道必答题。
- **`chNN_*.md` 对比文档**：微观、按"代码执行顺序"、贴完整手写代码、对比具体片段。

两者**互补**，不重复：README 不贴代码、对比文档不答必答题。
